# Lucky Game — Fixed End-to-End Master Plan (TH)
Baseline: 25 Nov 2026. Active repository: `jtkmanga/Lucky-Game-GDevelop`, branch `main`. **No new repo necessary.**
This is the execution sequence to reach a playable, secure online launch without restarting work or expanding scope.

## Definition of done for the whole project
A player opens the existing visual UI v12, signs in with Google via Supabase Auth, joins a server-owned Free 4 or authorized VIP 2 room, plays the authoritative 0→100 turn rules and one Lucky Box, reconnects safely, receives durable winner/box points, sees per-mode leaderboards and correct Bangkok resets; Admin can securely monitor/edit, and real VIP/item payment is verified and audited. Staging passes automated checks then a controlled production launch. The 10,000 CCU / 24h×30d study is a separate capacity and cost gate, NOT an untested launch guarantee.

## Phase P1 — Single database and authentication design (IN PROGRESS / highest priority)
1. [ ] Inspect Supabase Auth/provider settings via connector and currently empty schema; identify which provider options can be managed with connector and which need Google OAuth consent setup in browser.
2. [ ] Define private `game` PostgreSQL schema: player profile (Supabase `auth.users.id` UUID as identity), VIP entitlements, rooms/seats/checkpoints, immutable score ledger, turn/outbox receipts, current rankings and archive snapshots, admin audit log, order/payment records.
3. [ ] Enforce RLS in any exposed `public` schema; preferably keep all game writes inside unexposed `game` schema controlled by server credentials. Never send SQL admin credentials or service-role key to browser. Supply reviewed migrations and rollback notes. Applying migrations is a separate mutating action, document clearly.
4. [ ] Replace `backend/railway/secure-server.cjs` Firebase verifier with Supabase Auth/JWT validation, including issuer, audience, expiry, signature/JWKS or `getUser` server validation; use verified `auth.users.id` as room seat UID.
5. [ ] Replace Firebase browser bridge generated by `tools/prepare_railway_secure.py` with Supabase Google OAuth and compatible WSS join/resume; preserve the visible HTML v12 layout.
6. [ ] Make server fail closed when required env/provider/database config is missing; provide `.env.example` without secrets.
**Exit:** source wired across browser/WS/DB with no Firebase dependency in active build; scope evidence separately for isolated tests and real staging acceptance.

## Phase P2 — Authoritative gameplay (PENDING)
1. [ ] Consolidate Node game source from ZIP into editable tracked text (do not lose original); keep original UI unchanged.
2. [ ] Free=4/VIP=2 segregated matchmaking, ensure verification and VIP entitlement before queue, stable unique room IDs.
3. [ ] Server random dice 1–6; 20 seconds/turn then SKIP (never auto-roll); reject duplicate/late/out-of-turn commands; snake/ladder/overshoot win +10.
4. [ ] Exactly 1 Lucky Box/game, only landing player opens; no duplicate rewards; show award near player name and event log.
5. [ ] Add **five distinct authoritative board maps**, random pick per game, consistently rendered on all clients.
6. [ ] Serialized single writer per room, durable revision/CAS, atomic turn+score/outbox before broadcasting; on DB errors do not broadcast ghost result.
**Exit:** all gameplay flows implemented in source and attached to real Auth/DB. No "working live" claim until verified.
