# P3 archive cutover research checkpoint (isolated Staging only)
 
**Not a migration / Do not deploy.** Audit of the generated VIP2 acceptance artifact at `5897a976`: only one packaged insertion uses `game.score_events` (fenced turn, receipt and room revision committed together), but the running constructor calls the ordinary path. The reachable controller calls it once. The separate legacy packaged adapter uses the unqualified old `lucky_score_events` table and is not imported by the secure server. Administrative and payment prototypes must be enumerated independently before future integration. Managed Staging confirmed zero enabled ledger write triggers and zero archive rows; runtime can directly INSERT ledger and cannot read archive. None of this is sufficient to declare closed periods final.
 
The candidate SQL trigger makes direct/bypassed ledger inserts fail before INSERT unless their timestamp matches the awarding transaction and the existing canonical private predicate says the period is open. That predicate checks the gameplay login, canonical period boundaries, the session's shared period lock and previous non-overlapping archives under its dedicated policy. No change to rows, current schedule, game points, UI, ledger permissions, or running system is authorized by this proposal. It deliberately blocks backdated admin corrections and all unfenced writers. A superuser or DDL owner can still change schema (not an in-app privilege).
 
## Sequence before a managed cutover
 
1. On native PostgreSQL 17, use disposable, TLS-verified physical sessions with the exact pinned writer/closer/reader and managed role layout. Assert an unmodified unfenced writer and direct insert are rejected without changing room revision or receipt. Assert Free and VIP locked writers succeed; wrong mode, wrong lock, mismatched timestamp, missed boundary, unknown predicate fail. Test archive’s exclusive lock against a concurrent shared writer before midnight, including PostgreSQL commit acknowledgement loss and immutable once-only snapshot readback. Also test whether a closer arriving before a transaction ends waits/polls safely; no early snapshot on a lock miss.
2. Before changing the Staging database, drain old writers (including jobs and manual admin/repair), verify there are no unfinished rooms or in-flight awards, snapshot grant/ledger metadata, and validate exact intended clients. Make role provisioning for the canonical void-free predicate, the fail-closed trigger, and switching the app writer an independently reviewed operational cutover, not part of VIP testing.
3. Only after the managed rehearsal passes, enable the separate callable closer and limited reader in Staging. Route final archive only when complete; keep history labelled provisional otherwise. Keep real payments, Production and scheduled work disabled. If a rollback is needed, stop closer first. Never reopen unfenced writes underneath published immutable snapshots.

Managed read-only preflight returned **4/4** boundary calculations (1 ms before and exactly at Bangkok midnight, Free weekly Sunday and VIP daily), zero archive rows and zero enabled ledger triggers. This checks only the SQL calendar computation. The proposed trigger and actual concurrent writer/closer cutover were not executed.
